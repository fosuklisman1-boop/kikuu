# TheTeller Payment Gateway — Design

## Goal

Add TheTeller (a Ghanaian payment gateway, `checkout.theteller.net`) as a second payment option alongside the existing Paystack integration. Admins control which gateway(s) are active via a settings toggle; checkout shows a choice only when both are enabled, otherwise silently uses whichever one is. Since TheTeller's documented API has no server-to-server webhook (only a browser redirect plus a pollable `/status` endpoint), a scheduled reconciliation job catches orders that would otherwise get stuck `pending` if a shopper pays but never completes the redirect.

## Existing Pattern This Extends

Confirmed by reading the current code:

- `lib/paystack.ts` — thin fetch wrapper: `initializePayment`, `verifyTransaction`, `validateWebhookSignature`, `generateReference`.
- `app/api/checkout/route.ts` — creates the `orders` row (`status: 'pending'`, `payment_type: 'paystack'`, `payment_status: 'pending'`), calls `initializePayment`, stores the returned reference on the order (`paystack_reference`), returns `{ access_code, reference, order_id, ... }` to the client.
- `components/store/CheckoutForm.tsx` — on the Paystack response, opens Paystack's **inline JS popup** via `new PaystackPop().newTransaction({ accessCode: data.access_code })` — no page navigation.
- `app/api/payment/verify/route.ts` — shared `processVerification(admin, orderId, reference)`: re-fetches the order, re-verifies via `verifyTransaction`, does an atomic `pending`→`paid` update (guarded by `.eq('status', 'pending')` to avoid double-processing if the webhook already ran), decrements stock for non-preorder items, calls `creditShopEarnings`. Has both a `GET` (browser redirect fallback) and `POST` (inline-popup callback) handler.
- `app/api/webhooks/paystack/route.ts` — signature-verified webhook, does the identical atomic update independently, as a second, race-safe path to the same outcome.
- `orders.payment_type` already exists as `'paystack' | 'cod'` (added in migration 008) — this is the natural column to extend, not a new one.

TheTeller's flow (per TheTeller's own docs) is structurally similar but has two real differences: (1) it's a **redirect to a hosted page**, not an inline popup — `POST /initiate` returns a `checkout_url` to navigate to, not an access code; (2) there is **no documented webhook** — only the browser redirect (`?code=&status=&reason=&transaction_id=`) and a pollable `GET /v1.1/users/transactions/{id}/status`. This is why a reconciliation job is part of this design, not optional polish.

## Schema Change

One migration, `supabase/migrations/020_theteller_payment_gateway.sql`:

```sql
-- Extend the existing payment_type check to allow 'theteller'
ALTER TABLE public.orders DROP CONSTRAINT IF EXISTS orders_payment_type_check;
ALTER TABLE public.orders ADD CONSTRAINT orders_payment_type_check
  CHECK (payment_type IN ('paystack', 'cod', 'theteller'));

-- TheTeller's own transaction ID (12 digits, generated by us), set at checkout
-- time and matched against on verification — the direct equivalent of the
-- existing paystack_reference column, kept separate rather than merged since
-- they have different formats and different lookup call sites.
ALTER TABLE public.orders ADD COLUMN theteller_transaction_id text;

-- Admin-controlled gateway availability — same singleton pattern as the
-- existing withdrawal_settings table.
CREATE TABLE public.payment_gateway_settings (
  id boolean PRIMARY KEY DEFAULT true CHECK (id = true),
  paystack_enabled boolean NOT NULL DEFAULT true,
  theteller_enabled boolean NOT NULL DEFAULT false,
  updated_at timestamptz NOT NULL DEFAULT now()
);
INSERT INTO public.payment_gateway_settings (id) VALUES (true);

ALTER TABLE public.payment_gateway_settings ENABLE ROW LEVEL SECURITY;
-- No public read policy — this is read only via the admin-client server
-- action below, matching withdrawal_settings' own access pattern.
```

No existing order is affected — `payment_type` keeps defaulting to `'paystack'`, `theteller_transaction_id` is nullable and only ever set on TheTeller orders.

## `lib/theteller.ts`

Mirrors `lib/paystack.ts`'s shape exactly:

```ts
const THETELLER_BASE = process.env.THETELLER_LIVE === 'true'
  ? 'https://checkout.theteller.net'
  : 'https://checkout-test.theteller.net'

const MERCHANT_ID = process.env.THETELLER_MERCHANT_ID!
const API_USER = process.env.THETELLER_API_USER!
const API_KEY = process.env.THETELLER_API_KEY!

function authHeader(): string {
  return 'Basic ' + Buffer.from(`${API_USER}:${API_KEY}`).toString('base64')
}

export interface InitiatePaymentParams {
  email: string
  amount: number // in GHS
  transactionId: string // exactly 12 digits
  desc: string
  redirectUrl: string
}

export interface InitiateResult {
  checkoutUrl: string
  token: string
}

export async function initiatePayment(params: InitiatePaymentParams): Promise<InitiateResult> {
  const res = await fetch(`${THETELLER_BASE}/initiate`, {
    method: 'POST',
    headers: {
      'Content-Type': 'application/json',
      Authorization: authHeader(),
      'Cache-Control': 'no-cache',
    },
    body: JSON.stringify({
      merchant_id: MERCHANT_ID,
      transaction_id: params.transactionId,
      desc: params.desc,
      amount: params.amount.toFixed(2),
      redirect_url: params.redirectUrl,
      email: params.email,
      API_Key: API_KEY,
      apiuser: API_USER,
    }),
  })
  const json = await res.json()
  if (json.status !== 'success') throw new Error(json.reason || 'TheTeller initiate failed')
  return { checkoutUrl: json.checkout_url, token: json.token }
}

export interface TransactionStatusResult {
  status: string // 'approved' | other
  code: string // '000' = success
  transactionId: string
  amount: number
}

export async function checkTransactionStatus(transactionId: string): Promise<TransactionStatusResult> {
  const res = await fetch(
    `${THETELLER_BASE}/v1.1/users/transactions/${encodeURIComponent(transactionId)}/status`,
    {
      headers: {
        'Content-Type': 'application/json',
        'Merchant-Id': MERCHANT_ID,
        'Cache-Control': 'no-cache',
      },
    }
  )
  const json = await res.json()
  return {
    status: json.status,
    code: json.code,
    transactionId: json.transaction_id,
    amount: Number(json.amount),
  }
}

// TheTeller requires exactly 12 digits. Timestamp (13 digits) + 3 random
// digits, taking the last 12 — sufficiently unique for practical purposes;
// the DB doesn't uniquely constrain this column (matching how
// paystack_reference isn't uniquely constrained either), so a rare collision
// would surface as a verify-time mismatch, not silent data corruption.
export function generateTransactionId(): string {
  const timestamp = Date.now().toString()
  const random = Math.floor(Math.random() * 1000).toString().padStart(3, '0')
  return (timestamp + random).slice(-12)
}
```

**Endpoint choice** (`THETELLER_LIVE`): explicit env flag rather than piggybacking on `NODE_ENV`, since `NODE_ENV` is `'production'` in every Vercel deployment including preview URLs — you want the ability to test against TheTeller's test endpoint even from a production build, until you're ready to flip it.

**New env vars** (you set the real values in `.env.local`/Vercel, same as `PAYSTACK_SECRET_KEY` already works — never pasted into chat or committed): `THETELLER_MERCHANT_ID`, `THETELLER_API_USER`, `THETELLER_API_KEY`, `THETELLER_LIVE`.

## Gateway Settings — Read Action and Admin UI

`lib/actions/payment-settings.ts` (plain read/write actions, `'use server'`):

```ts
export async function getPaymentGatewaySettings(): Promise<{ paystackEnabled: boolean; tellerEnabled: boolean }> {
  const admin = createAdminClient()
  const { data } = await admin.from('payment_gateway_settings').select('*').eq('id', true).single()
  return {
    paystackEnabled: data?.paystack_enabled ?? true,
    tellerEnabled: data?.theteller_enabled ?? false,
  }
}

export async function updatePaymentGatewaySettings(formData: FormData): Promise<{ error?: string }> {
  await requireAdmin()
  const paystackEnabled = formData.get('paystack_enabled') === 'on'
  const tellerEnabled = formData.get('theteller_enabled') === 'on'
  if (!paystackEnabled && !tellerEnabled) {
    return { error: 'At least one payment gateway must stay enabled.' }
  }
  const admin = createAdminClient()
  const { error } = await admin
    .from('payment_gateway_settings')
    .update({ paystack_enabled: paystackEnabled, theteller_enabled: tellerEnabled })
    .eq('id', true)
  if (error) return { error: error.message }
  revalidatePath('/admin/payments')
  revalidatePath('/checkout')
  return {}
}
```

New admin page `app/admin/payments/page.tsx` + `components/admin/PaymentGatewayForm.tsx` — a simple two-checkbox form, same shape as the existing `MinAmountForm.tsx` pattern in `/admin/withdrawals`. The "at least one enabled" guard is the only real validation — it exists so an admin can never accidentally break checkout entirely.

## Checkout Flow

**`app/api/checkout/route.ts`** changes:
- `CheckoutSchema`'s `payment_type` field changes from `z.literal('paystack').default('paystack')` to `z.enum(['paystack', 'theteller']).default('paystack')`.
- Before creating the order, fetch `getPaymentGatewaySettings()` and reject the request (400) if the client-requested gateway isn't actually enabled — never trust the client-sent value alone, exactly the same discipline already used for shop/price validation elsewhere in this route.
- The order insert sets `payment_type` to the validated (not client-trusted-blind) value.
- After the order is created, branch:
  - `paystack` (unchanged): `initializePayment` → store `paystack_reference` → return `{ access_code, reference, ... }`.
  - `theteller`: `generateTransactionId()` → `initiatePayment({ transactionId, redirectUrl: \`${NEXT_PUBLIC_APP_URL}/api/payment/theteller-verify?order_id=${order.id}\`, ... })` → store `theteller_transaction_id` → return `{ checkout_url, order_id, ... }`.
- Same ghost-order cleanup on gateway-init failure (delete the order) that already exists for the Paystack path.

**`components/store/CheckoutForm.tsx`** changes:
- Reads `getPaymentGatewaySettings()` on mount (or receives it as a server-fetched prop from the checkout page — cheaper, no extra client round-trip). If only one gateway is enabled, no UI shown, request always sends that one. If both are enabled, a simple radio selector ("Pay with Card / Bank" vs "Pay with Mobile Money") — copy exact wording is a small detail to settle during implementation, not architecturally significant.
- On a `theteller` response, instead of the existing `PaystackPop` popup call, do `window.location.href = data.checkout_url` — a full-page redirect to TheTeller's hosted checkout, mirroring how Paystack's own `GET` verify fallback already handles browser-redirect-style completion.

## Verification — Shared Logic, Two Entry Points

`processVerification` in `app/api/payment/verify/route.ts` is generalized to branch on the order's own `payment_type` rather than assuming Paystack — this is a refactor of existing logic, not a duplication:

```ts
async function processVerification(
  admin: SupabaseAdmin,
  orderId: string,
  reference: string
): Promise<{ ok: true } | { ok: false; error: string; code?: string }> {
  const { data: order } = await admin.from('orders').select('*').eq('id', orderId).single()
  if (!order) return { ok: false, error: 'Invalid order', code: 'invalid_order' }

  const expectedReference = order.payment_type === 'theteller'
    ? order.theteller_transaction_id
    : order.paystack_reference
  if (expectedReference !== reference) {
    return { ok: false, error: 'Invalid order or reference', code: 'invalid_order' }
  }

  if (order.status !== 'pending') return { ok: true }

  const result = order.payment_type === 'theteller'
    ? await checkTransactionStatus(reference).then(r => ({
        success: r.code === '000',
        amountPesewas: Math.round(r.amount * 100),
        channel: 'theteller',
      }))
    : await verifyTransaction(reference).then(r => ({
        success: r.status === 'success',
        amountPesewas: r.amount,
        channel: r.channel,
      }))

  // ...the existing amount-mismatch check, atomic pending->paid update,
  // stock decrement, and creditShopEarnings call are UNCHANGED below this
  // point — they already operate on the generic { success, amountPesewas,
  // channel } shape this normalizes both providers into.
}
```

**New route** `app/api/payment/theteller-verify/route.ts` — a thin `GET` handler matching TheTeller's redirect shape (`?order_id=&transaction_id=&code=&status=`), calling the same `processVerification`, then redirecting to `/orders/{orderId}?success=1` or `?error=...` exactly like the existing Paystack `GET` handler does. TheTeller has no inline-popup equivalent, so there's no `POST` handler needed here (unlike the Paystack verify route, which has both).

**Paystack's existing webhook** (`app/api/webhooks/paystack/route.ts`) is untouched — it's Paystack-signature-specific and stays that way. TheTeller gets no webhook route, since TheTeller doesn't send one; its second line of defense is the reconciliation job below, not a webhook.

## Reconciliation Cron

**Problem this solves:** if a shopper completes payment on TheTeller's hosted page but closes their browser before the redirect back to `/api/payment/theteller-verify` completes, the order stays `pending` forever with nothing else to notice.

**`app/api/cron/reconcile-theteller/route.ts`:**

```ts
export async function GET(req: NextRequest) {
  const authHeader = req.headers.get('authorization')
  if (authHeader !== `Bearer ${process.env.CRON_SECRET}`) {
    return NextResponse.json({ error: 'Unauthorized' }, { status: 401 })
  }

  const admin = createAdminClient()
  const tenMinutesAgo = new Date(Date.now() - 10 * 60 * 1000).toISOString()

  const { data: staleOrders } = await admin
    .from('orders')
    .select('id, theteller_transaction_id')
    .eq('payment_type', 'theteller')
    .eq('status', 'pending')
    .lt('created_at', tenMinutesAgo)
    .not('theteller_transaction_id', 'is', null)

  const results = []
  for (const order of staleOrders ?? []) {
    const result = await processVerification(admin, order.id, order.theteller_transaction_id!)
    results.push({ orderId: order.id, ok: result.ok })
  }

  return NextResponse.json({ checked: results.length, results })
}
```

Ten-minute grace period so it never races an order that's still legitimately mid-checkout. Reuses the exact same `processVerification` — an order that reconciles as failed goes through the identical cancel-and-record path a normal failed verification would.

**`vercel.json`** (new file, none exists yet):

```json
{
  "crons": [
    { "path": "/api/cron/reconcile-theteller", "schedule": "*/5 * * * *" }
  ]
}
```

Every 5 minutes. `CRON_SECRET` is a new env var you set yourself; Vercel automatically sends it as the `Authorization` header on cron-triggered requests once the env var exists — this is Vercel's standard, documented convention, not custom auth logic.

## Testing

- `lib/theteller.ts`: `generateTransactionId()` is the only pure, testable piece (produces exactly 12 digits, format-checkable) — `lib/theteller.test.ts` mirrors `lib/wallet-earnings.test.ts`'s style. `initiatePayment`/`checkTransactionStatus` are thin fetch wrappers with no branching logic of their own (matching `lib/paystack.ts`'s existing untested state) — not unit tested, consistent with this codebase's established convention of not mocking external HTTP calls.
- Manual verification against TheTeller's **test** endpoint (`THETELLER_LIVE` unset/false) before any live-endpoint testing: place a real order through the TheTeller path, confirm redirect to their hosted page, complete a test payment, confirm the redirect back lands on the order confirmation page with the order marked `paid`.
- Reconciliation job: manually trigger `GET /api/cron/reconcile-theteller` with the correct `Authorization` header against a deliberately-stuck test order (e.g., abandon the TheTeller checkout page without completing it, then complete it via TheTeller's test tools if available, then trigger the cron manually rather than waiting 5 minutes) to confirm it correctly picks up and reconciles a stale order.

## Global Constraints

- Every server action derives admin scope via `requireAdmin()` — the settings write action, matching the rest of this codebase's convention.
- The cron route is the one new *unauthenticated-by-Supabase-session* endpoint in this plan — protected instead by `CRON_SECRET`, matching Vercel's own documented cron-auth pattern. It must reject any request without the correct bearer token before touching the database.
- Never trust a client-sent `payment_type` without cross-checking `payment_gateway_settings` server-side first.
- This is money-movement code — every task touching `app/api/checkout/route.ts`, `app/api/payment/verify/route.ts`, the new `theteller-verify` route, or the reconciliation cron requires the same rigor this codebase has applied to every other payment-adjacent change this session: a real `npm run build`, careful hand-traced scenario verification (an order paid via TheTeller, an order abandoned mid-TheTeller-checkout then reconciled, an order where the client lies about which gateway is enabled), and no shortcuts on the idempotency guard (`processVerification`'s existing `.eq('status', 'pending')` atomic-update pattern must keep protecting BOTH gateways identically — a TheTeller order verified twice, once via the redirect and once via the reconciliation cron racing it, must never double-process, exactly like the existing Paystack verify-vs-webhook race is already protected).
